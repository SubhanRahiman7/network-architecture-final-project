# PBF/1 design notes

[SPEC.md](../SPEC.md) says *what* the protocol is. This file records *why* each choice was made and what was rejected.

## Choices and the alternatives

| Choice | Alternative | Why this one |
|--------|-------------|--------------|
| 12-byte header, 32-bit Length | HTTP/2's 9 bytes with a 24-bit length | 24 bits bake a 16 MiB ceiling into the format. With 32 bits the ceiling is a *policy* (SPEC section 7) which a later version can raise without touching the layout. Four extra bytes per frame are negligible next to a file. |
| 4-byte Magic starting `0x7F` | 2-byte ASCII magic | `0x7F` starts neither an HTTP/1 request line (a letter) nor the HTTP/2 preface (`P`). A mismatched peer is detected on the first byte, and a lost frame boundary is almost impossible to mistake for a valid header. |
| Seq in the header, echoed by the server | Match responses by order only | Order is still guaranteed, but the echo lets a client *verify* the pairing and lets a dump show which exchange a frame belongs to. It costs 2 bytes. |
| Body = all remaining payload | Explicit body length | One length fewer to validate; two lengths can never disagree. `Content-Length` stays as a hint, as in HTTP, but is never trusted. |
| Ten **numbered** header names + length-prefixed literals | Spell every name; or full HPACK | These are HPACK's first two mechanisms (a static table, literals) without Huffman coding or a dynamic table. Numbering the ten names the programs really send saves 4-13 bytes per field (the client's request for `/hello.txt` shrinks from 65 to 45 payload bytes) and the table is tiny enough to copy exactly. A dynamic table would need shared mutable state across requests, which is a source of desync bugs and not worth it for a handful of headers. |
| Tag byte before every field (0 = literal) | Reserve high bit of the name length | One uniform rule, easy to explain, and tags 11..255 stay free for a later version (a new numbered name, or a new field kind). |
| Unknown frame types are skipped by Length | Close on unknown types | The one rule that leaves room for version 2: a later PING or SETTINGS frame cannot break a version-1 peer. |
| `400` keeps the connection | Close on any error | A bad *payload* does not lose the frame boundary, so the connection is still usable; only a bad magic/version or a cut frame (boundary lost) closes it. |
| Raw bytes for the path | Percent-encoding | A length-prefixed string can already hold any byte; encoding would add a decoder and a new class of malformed input. |
| GET only, method as one byte | Method string | The protocol fetches files. Other methods can be given numbers later; `405` already covers them. |
| Thread per connection in the server | One connection at a time | A client that connects and stays silent must not block everyone else. Each connection still has the 30 s idle timeout, and at most 64 connections are open at once. |

## What a receiver must never do

* Trust a length: every length is compared with its limit *and* with the bytes remaining before any allocation or copy.
* Treat a path as a filename: the server checks the raw path for `..` and `\`, resolves symlinks and verifies the
  result is inside the document root.
* Guess at a lost frame boundary: after bad magic/version, or a frame cut in the middle, the only safe action is to close.

## Why the example in the spec is verified, not written by hand

[HEXDUMP.md](../HEXDUMP.md) is generated by `tools/annotate.py` from the bytes the real client and server exchange, and
`tests/test.cpp` asserts the same bytes. Two independent programs written from SPEC.md alone (`tools/stranger_client.py`
and `tools/stranger_server.py`) talk to the C++ server and client in `make interop`; that is the check that PBF/1 is a
protocol and not just the behaviour of one implementation.
